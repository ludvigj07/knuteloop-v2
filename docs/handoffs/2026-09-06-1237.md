### Actual v1 deployment and code evidence

- `deploy/README.md:7` specifies a Hetzner Cloud VM, “CX22 eller større.” Helsinki and the actual purchased size are not established by this source.
- `deploy/README.md:42` places the JSON application database, SQLite auth store, uploads and releases on the same machine. `deploy/Caddyfile:16` routes API and uploads through Node. Image/video conversion also runs on that machine.
- `index.mjs:707` buffers the whole incoming JSON body, concatenates it, turns it into a string and parses it. `index.mjs:317` then decodes base64 media into a buffer. A 30 MiB video has approximately 40 MiB of base64 representation before the additional buffers and processing allocations; actual process RAM was not measured.
- A 50 MiB limit applies to the **whole JSON request**, not each decoded file. Video input is independently capped at 30 MiB.
- `index.mjs:539` already serializes ordinary video transcodes in the April 19 history. Do not claim unbounded simultaneous ordinary video encoders. Image/HEIC processing does not use that queue.
- `index.mjs:578` limits video duration to 20 seconds but does not explicitly cap server output dimensions, bitrate or bytes. Browser-side compression tries 720px/~1.5Mbps but can fall back to the original upload (`backend/src/data/api.js:185`). Input size therefore does not guarantee a small encoded output.
- `index.mjs:1874` builds a large bootstrap response from users/submissions and recomputes profiles, leaderboards and activity. New-submission count understates the work caused by browsing and background refreshes.
- Media serving uses streams/range requests and long browser-cache headers (`index.mjs:782`, `index.mjs:3598`). Do not claim each viewer requires a full video file to be held in server RAM.

### Storage accounting — avoid an invented multiplier

- Normal images become a 1600px WebP and a 480px thumbnail (`index.mjs:2044`); the original is not permanently retained by that path.
- Normal video conversion writes a temporary `.transcoded.mp4`, then replaces the original (`index.mjs:552`). Temporary double occupancy and queued originals exist, but normal successful uploads do not permanently retain original plus encoded video pairs.
- The backup script copies JSON/SQLite for 14 days, **not all media** (`deploy/knuteloop-backup.sh:10`). Five retained release directories share uploads through symlinks (`deploy/deploy.sh:21`); they do not imply five media copies. OS, dependencies/releases and logs still consume disk.
- Failure after saving a file but before storing its DB record can leave an orphan; no general sweep was found. No evidence quantifies how often this happened.
- Illustration only: 1,000 videos averaging 20 MB occupy 20 GB before other disk contents. That can exhaust a small machine's disk, but neither the 1,000-video count nor the 20 MB mean is established by the supplied report.

### Billing evidence

- [Hetzner Cloud billing FAQ](https://docs.hetzner.com/cloud/billing/faq/): server capacity has hourly billing and monthly caps; running more application requests is not itself a per-request compute charge. Volumes, snapshots and excess outgoing traffic are separate concerns. Merely powering off an old server does not end billing. These are things to check in an invoice, not assertions that abandoned resources existed.
- [Hetzner traffic policy](https://docs.hetzner.com/robot/general/traffic/): European CX/CPX/CAX Cloud plans list 20 TB included transfer. Standard dedicated root servers have unlimited traffic on their default 1 Gbit uplink; plan type matters. The actual plan/contract remains unknown.
- [June 15 price table, old/new columns](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/): before the June increase, listed Finland CPX plans ranged from EUR 7.99/month (CPX22) to EUR 50.49/month (CPX62), excluding IPv4/VAT. Much larger dedicated-resource plans existed at substantially higher prices. Do not apply June's new prices retrospectively to a May bill. This is a sanity check, not identification of the user's plan.
